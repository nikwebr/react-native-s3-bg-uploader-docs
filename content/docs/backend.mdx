For each file, the library calls the endpoints below.
Configure the endpoints to use by calling `setConfig` via the [API reference](/docs/api).

## startUpload

<div className="not-prose flex items-center gap-2 font-mono text-sm px-3 py-2 rounded-lg border bg-card w-fit my-4">
  <span className="text-xs font-semibold bg-primary/15 text-primary px-2 py-0.5 rounded">POST</span>
  <span className="text-muted-foreground">{`{startUploadApi}/`}</span>
</div>

Initiates a multipart upload for a single file.

**Request Body (JSON)**

```json
{
  "fileName": "video.mp4",
  "fileHash": "a1b2c3d4e5f6...",
  "fileSize": 104857600,
  ...userParams
}
```

| Field | Type | Description |
| --- | --- | --- |
| `fileName` | `string` | Original file name |
| `fileHash` | `string` | Hash of the **unencrypted** file. Omitted when `sendFileHash` is disabled (see below) |
| `fileSize` | `number` | Size of the local, **unencrypted** file in bytes |
| `encryption` | `object` | Only present for encrypted uploads: ciphertext format so the backend can derive the stored size. See [Encrypted uploads](#encrypted-uploads) |
| `...userParams` | `object` | Any additional params you passed via `uploadFile`, merged flat into the body |

`fileName`, `fileHash`, `fileSize` and `encryption` are reserved: values with those names inside
`...userParams` are ignored, so a caller cannot override the real file size or hash.

`fileHash` is sent by default. Pass `false` as the fourth argument of
`setConfig(startUploadApi, getUploadUrlsApi, completeApi, sendFileHash)` to omit it from this body.
The hash is still computed locally over the plaintext file and used for duplicate detection and
resume, so omitting it only changes what the backend receives.

**Response (JSON)**

```json
{
  "key": "uploads/abc123/video.mp4",
  "uploadId": "VXBsb2FkSWQ...",
  "partSize": 10485760
}
```

| Field | Type | Description |
| --- | --- | --- |
| `key` | `string` | Object key to use for all subsequent calls |
| `uploadId` | `string` | Upload ID for this file |
| `partSize` | `number` | Part size the uploader should use |

## getUploadUrls

<div className="not-prose flex items-center gap-2 font-mono text-sm px-3 py-2 rounded-lg border bg-card w-fit my-4">
  <span className="text-xs font-semibold bg-primary/15 text-primary px-2 py-0.5 rounded">POST</span>
  <span className="text-muted-foreground">{`{getUploadUrlsApi}/`}</span>
</div>

Should return URLs for a set of parts. These urls will be used by the library for uploading the file parts.
For example, you could return presigned S3 multipart upload urls.

**Request Body (JSON)**

```json
{
  "key": "uploads/abc123/video.mp4",
  "uploadId": "VXBsb2FkSWQ...",
  "parts": [1, 2, 3, 4]
}
```

| Field | Type | Description |
| --- | --- | --- |
| `key` | `string` | S3 object key from `startUpload` |
| `uploadId` | `string` | Multipart upload ID from `startUpload` |
| `parts` | `number[]` | Part numbers to get URLs for |

**Response (JSON)**

```json
{
  "urls": {
    "1": "https://bucket.s3.amazonaws.com/...?partNumber=1&...",
    "2": "https://bucket.s3.amazonaws.com/...?partNumber=2&...",
    "3": "...",
    "4": "..."
  }
}
```

| Field | Type | Description |
| --- | --- | --- |
| `urls` | `Record<string, string>` | Map of part number → presigned URL |

## upload 

<div className="not-prose flex items-center gap-2 font-mono text-sm px-3 py-2 rounded-lg border bg-card w-fit my-4">
  <span className="text-xs font-semibold bg-primary/15 text-primary px-2 py-0.5 rounded">PUT</span>
  <span className="text-muted-foreground">{`{uploadUrl}/`}</span>
</div>

**Request Body**
contains the file part

**Response**
Must provide an `Etag` header that identifies the uploaded part. This E-Tag will be re-provided by the library to the complete endpoint.

## complete

<div className="not-prose flex items-center gap-2 font-mono text-sm px-3 py-2 rounded-lg border bg-card w-fit my-4">
  <span className="text-xs font-semibold bg-primary/15 text-primary px-2 py-0.5 rounded">POST</span>
  <span className="text-muted-foreground">{`{completeApi}/`}</span><span>{`{uploadId}/{key}`}</span>
</div>

Finalizes the multipart upload after all parts have been uploaded.

**Request Body (JSON)**

```json
{
  "parts": [
    { "PartNumber": 1, "ETag": "abc123..." },
    { "PartNumber": 2, "ETag": "def456..." }
  ]
}
```

| Field | Type | Description |
| --- | --- | --- |
| `parts` | `Part[]` | List of completed parts, sorted by `PartNumber` |
| `parts[].PartNumber` | `number` | Part number |
| `parts[].ETag` | `string` | ETag returned by PUT upload response `Etag` header for that part |

**Response**

The response body is ignored. The library only expects an HTTP `2xx` status code.

## Encrypted uploads

`encryptAndUploadFile()` uses the same endpoints and the same request and response shapes as
`uploadFile()`. No endpoint needs to change, and the backend never receives key material or
plaintext.

For encrypted uploads the following details differ, because the library uploads ciphertext.

`fileHash` and `fileSize` in `startUpload` describe the **plaintext** file. The object stored in
the bucket is larger: each part gains the encryptor's per-part overhead, and the built-in cipher
appends a descriptor to the final part. `fileSize` therefore stays the plaintext size, which
remains meaningful for quotas and UI.

`partSize` returned by `startUpload` is the maximum **ciphertext** size of one part. The uploader
reduces the plaintext chunk size to `partSize - reserved`, so the number of parts can be higher
than `ceil(fileSize / partSize)`. If `partSize` is not larger than `reserved`, upload preparation
fails instead of uploading.

### Deriving the stored size

For encrypted uploads the `startUpload` body additionally carries an `encryption` object with the
format numbers of the scheme that encrypts this upload. The client does not send the stored size;
the backend derives it from the `partSize` it returns:

```json
{
  "fileName": "video.mp4",
  "fileHash": "a1b2c3d4e5f6...",
  "fileSize": 31457280,
  "encryption": { "overhead": 16, "hasFooter": true, "footerLen": 28 }
}
```

| Field | Type | Description |
| --- | --- | --- |
| `encryption.overhead` | `number` | Ciphertext bytes added to every part (AEAD tag, IV prefix, …) |
| `encryption.hasFooter` | `boolean` | Whether the wire format ends with a descriptor inside the final data part |
| `encryption.footerLen` | `number` | Bytes that descriptor occupies |

```text
reserved     = overhead + (hasFooter ? footerLen : 0)  // reserved in every part
effective    = partSize - reserved                     // plaintext bytes per part
dataParts    = ceil(fileSize / effective)              // at least 1 if hasFooter
storedBytes  = fileSize + overhead * dataParts + (hasFooter ? footerLen : 0)
```

Both the per-part overhead and the descriptor are reserved in every part, because the descriptor
rides inside the last data part.

See [End-to-end encryption](/docs/encryption) for the wire format and custom encryptor contract.
